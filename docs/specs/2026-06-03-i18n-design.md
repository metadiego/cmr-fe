# i18n — Multi-language (Spanish + English) — Design

**Date:** 2026-06-03
**Status:** Approved

## Goal & scope
Make the FE multi-language (CONSIDERACIONES-FE #14). The UI was authored 100% in
hardcoded **Spanish**; this extracts every visible string into per-locale dictionaries, adds an
**English** translation, and a language switcher. Spanish stays the default (visible UI unchanged),
but everything now comes from dictionaries and is switchable ES↔EN. New development is authored with
**English keys**.

**In scope:** `next-intl` setup (cookie-based, **no URL routing**); `es`/`en` dictionaries;
migration of all current strings (landing, login, dashboard, header/nav, search, mode-toggle,
api-health-check); `<html lang>` dynamic; a `LanguageToggle`; ICU date/currency/timezone formatting
defaults. **Out of scope:** per-user language persisted in the BE (future, #51); locale-prefixed
URLs; translating BE-sourced error messages (those come from the API verbatim).

## Decisions
- **Library: `next-intl@4.13.0`** — Next 16 compatible (`peerDeps.next` includes `^16`); ICU
  formatting for #14; works in Server + Client Components. Native `getDictionary` was rejected
  because the official pattern forces `app/[lang]/` routing (would break `(app)`, the gating in
  `proxy.ts`, and the hardcoded `redirect()`s) and ships no formatting helpers.
- **Cookie-based, NO i18n routing.** Locale lives in the `NEXT_LOCALE` cookie; URLs and routes are
  untouched. This mode needs **no middleware**, so **`proxy.ts` is not modified** (session refresh +
  gating intact).
- **Default `es`** (untagged visitor sees Spanish, as before).

## Approach (Next 16 + next-intl)
- `i18n/request.ts` (`getRequestConfig`): reads `NEXT_LOCALE` via **`await cookies()`** (Next 16:
  async), returns `{ locale, messages, timeZone, formats }`.
- `app/layout.tsx` is **async**: `<html lang={await getLocale()}>` + `<NextIntlClientProvider>`
  (no props — inherits locale/messages from request config; v4 server provider).
- Server Components/Actions: `getTranslations(ns)`. Client Components: `useTranslations(ns)` /
  `useFormatter()` / `useLocale()`.
- `LanguageToggle` (client) calls the `setLocale` Server Action (writes the cookie) then
  `router.refresh()` to re-render Server Components under the new locale.

## Edge cases
- Unknown/missing cookie → `defaultLocale` (`es`).
- Rich strings (`<code>`, `<kbd>`) use `t.rich(...)` with tag callbacks.
- BE error messages (Supabase / ApiError) are shown verbatim — not translated.
- Pages become dynamic (`ƒ`) since they read the cookie — acceptable for an authed app.
